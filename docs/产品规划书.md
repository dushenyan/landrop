# 局域网设备间文件与媒体传输工具产品规划书

## 一、我们要解决什么问题

你手上有三台设备：一台电脑、一部 iPhone、一台 iPad。

照片在平板上，想发到电脑上修图。修好的成片在电脑，想传到手机上看。今天你得怎么做？打开平板上的聊天软件，登录，找到电脑对应的账号，发送；再到电脑上登录另一个软件接收。传视频更麻烦，很多聊天软件会压缩，传过去已经是另一张脸。

问题不在设备，缺的是一个统一的「中转站」。

我们打算做这样一个工具：在局域网里放一台常驻服务器，所有设备都连到它。任何一台设备把文件传上去，其他设备就能看到。传的是原文件，不压缩。每次上传都留一个版本，服务器上随时能翻旧账。

**打个比方**：这就像在公司前台放一个收发室。谁都能把东西送来，贴上标签，别人来取。收发室记录了每一件东西的来历和每次送来的时间。你不用再挨个给同事发消息问「收到了吗」。

## 二、产品定位

一句话定位：**局域网内的私有媒体中转站，传原图、留版本、全设备可见。**

它有三个特点，也是我们和聊天软件、和 AirDrop 的根本区别。

- **不压缩**：图片、视频传的就是原文件。服务器只生成缩略图给你看，原文件一个字节都不动。
- **留版本**：同名文件反复传，每一次都作为独立版本存下来，可以随时翻出来、下载。
- **看得见**：所有文件集中躺在服务器的媒体库里，按图片、视频、文字、其他文件分类，一眼看全。

产品代号暂定 **LanDrop**（局域网投递）。名字可以改，不影响设计。

### 用户场景

| 场景 | 今天怎么做 | 用了之后 |
|---|---|---|
| 平板拍照发电脑 | 找聊天软件、登录、发送、压缩 | 平板扫码连入，选「发全员」，电脑直接看到原图 |
| 电脑成片发手机 | 换一个软件重复上述流程 | 电脑上选中，勾选「我的 iPhone」，手机收到 |
| 找三个月前的某张旧图 | 翻聊天记录，翻相册，找不到 | 媒体库搜索，按日期和来源设备筛选，点开历史版本 |
| 传一段 4K 视频 | 微信压成 480p | 原文件上传，手机在线看缩略图，需要时下原片 |

## 三、竞品调研：能抄什么，不能抄什么

我们调研了市面上几类代表项目。结论是：**没有现成项目同时满足「服务器中转 + 版本管理 + 媒体库浏览」这三点**，但每一块都有成熟的轮子可以借鉴。

| 项目 | 许可证 | 架构 | 可借鉴 | 不适合我们的地方 |
|---|---|---|---|---|
| [LocalSend](https://github.com/localsend/localsend) | Apache-2.0 | Flutter 客户端，设备间点对点直传 | REST 传输协议、mDNS + HTTP 双发现、SHA-256 校验、每文件 token | 点对点，没有服务器；没有版本管理；Flutter 技术栈不符 |
| [PairDrop](https://github.com/schlagmichdoch/PairDrop) | GPL-3.0 | 浏览器 PWA，WebRTC 点对点，Node 信令服务器 | Node 信令服务的写法、同网段按 IP 分组发现、接收确认交互 | 文件不落服务器，没有媒体库；iOS Safari 的 WebRTC 支持有历史坑 |
| [Syncthing](https://github.com/syncthing/syncthing) | MPL-2.0 | Go，块级同步 | 版本向量做变更标识、四种版本淘汰策略、块级哈希做增量 | 同步模型不等于一键发送；每台设备各存一份，版本不集中 |
| [Nextcloud](https://github.com/nextcloud/server) | AGPL | PHP 服务端，自带版本与相册 | `files_versions` 的归档命名、Photos 媒体库的产品形态 | 太重，部署复杂，不是局域网轻量工具 |

**一句话总结**：传输协议抄 LocalSend 的简单思路，版本化的数据模型抄 Syncthing 和 Nextcloud，服务器中转的形态参考 Portal 这种「协调与数据分离」的设计，产品体验对齐 Nextcloud 的相册。

关于设备发现，有一个关键事实必须先讲清楚。

## 四、一个绕不开的限制：iPhone 没法自动发现服务器

我们希望手机打开网页就自动列出局域网的服务器。调研下来，这在纯网页形态下做不到。

原因有三层：

- 浏览器的 JavaScript 发不出 UDP 组播，也没法枚举 Bonjour 服务。mDNS 只能跑在服务器上。
- 苹果从 iOS 14 起加了本地网络权限（见 [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy)），主要管原生 App。Safari 网页没有对应的权限申请接口，还有「本地网络页面被拦却不弹窗」的实测案例。
- 局域网 IP 走 HTTP，浏览器不认为是安全上下文（见 [MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts)）。这意味着 Service Worker 注册不了，网页里也调不起摄像头，算不上真正的 PWA。

**那怎么办？** 我们不跟这个限制硬碰，改成分层方案。

**第一层：给服务器一个固定地址。** 在路由器里做 DHCP 保留，让服务器每次都拿到同一个内网 IP。这是地基，地址不变，后面所有的二维码和书签才长期有效。

**第二层：服务器用 mDNS 广播自己。** 用 [bonjour-service](https://www.npmjs.com/package/bonjour-service) 发布一个 `_http._tcp` 服务，TXT 里只放路径和版本号，不放密钥。这层主要服务电脑和桌面客户端，让它们能自动发现。手机端不依赖它。

**第三层：手机用二维码配对，这是主入口。** 服务器屏幕上常驻一个二维码，内容是 `http://<内网IP>:<端口>/p/<一次性令牌>`。iPhone 用自带相机一扫，跳转 Safari，点一次「连接」就完成配对。令牌 5 分钟过期。没有相机的话，旁边配一个 6 位配对码，手动输一次。

配对完成后，提示用户「添加到主屏幕」。下次从桌面点开，就是真正的一点即开。

> 我的判断：牺牲手机端「零点击自动发现」的科幻感，换跨平台确定性，这笔账划算。工具的价值在于每次都能连上，不在于第一次少点一下。

## 五、技术选型

第一版的原则是**怎么好部署怎么来**。全部技术都选 Node.js 生态，一条命令启动，不碰容器。

### 前端

| 用途 | 选型 | 理由 |
|---|---|---|
| 脚手架 | Vite + React + TypeScript | 纯内网工具，不需要 SEO；构建产物就是一个 `dist` 目录，扔给后端托管即可（[Vite 文档](https://vite.dev/guide/)） |
| 上传 | Uppy（core + Dashboard + tus 插件） | 唯一同时满足多文件、进度条、大文件断点续传、移动端友好的现成方案（[Uppy](https://uppy.io/)） |
| 媒体库 | react-photo-gallery + yet-another-react-lightbox | 前者做瀑布流，后者支持原图缩放、视频、下载插件 |
| 实时状态 | socket.io | 设备上线、传输进度都要服务端主动推；它自带自动重连和心跳 |
| 状态管理 | Zustand + TanStack Query | 服务端数据交给 Query 缓存，界面状态交给 Zustand。第一版不上 Redux |
| 样式 | Tailwind CSS + shadcn/ui | bundle 小，移动端适配省心 |

移动端有三个细节必须做对：viewport 加 `viewport-fit=cover`，底部操作栏用 `env(safe-area-inset-bottom)` 避开 Home 条；拍照和录像拆成两个独立的 file input，iOS 上混在一起不会弹选择面板；高度用 `100dvh`，避开地址栏遮挡。

### 后端

| 用途 | 选型 | 理由 |
|---|---|---|
| Web 框架 | Express | 最成熟，tus 官方给了 Express 集成示例；`res.sendFile` 自带 Range 支持，视频能拖动播放 |
| 大文件上传 | tus 协议（`@tus/server` + `@tus/file-store`） | 基于 HTTP 的断点续传协议，浏览器关了、网断了都能接着传（[tus-node-server](https://github.com/tus/tus-node-server)）。局域网虽然快，但 iPhone 锁屏和切后台会打断传输，这个能力是刚需 |
| 元数据库 | Node 内置 `node:sqlite` | Node 22.5+ 自带，零安装、零编译、单文件。我们的 Node 是 22.22，直接用（[Node 文档](https://nodejs.org/api/sqlite.html)） |
| 文件存储 | 内容寻址（CAS）：按 SHA-256 分目录 | 相同内容只存一份，天然去重；版本表只记元数据 |
| 图片处理 | sharp | 自带预编译二进制，支持 iPhone 的 HEIC/HEIF，能按 EXIF 自动转正 |
| 视频缩略图 | ffmpeg（系统已装 9.0.2） | 抽取首帧做封面。失败就退化成通用图标，不阻断主流程 |
| 设备广播 | bonjour-service + qrcode | 前者发 mDNS，后者生成配对二维码 |

**为什么不用 WebRTC 点对点？** PairDrop 那条路很优雅，文件不落服务器。但我们的核心需求恰恰是「服务器上能看到所有媒体和版本」，文件必须经过服务器。既然如此，直接 HTTP 上传比 WebRTC 简单得多，也没有 iOS 上 WebRTC 的兼容性风险。

## 六、系统架构

```text
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  iPhone     │  │   iPad      │  │  电脑浏览器  │
│  (Safari)   │  │  (Safari)   │  │             │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │  扫码配对 / HTTP + WebSocket     │
       └──────────────┼──────────────────┘
                      ▼
         ┌────────────────────────────┐
         │   一台常驻机器（Node.js）    │
         │  ┌──────────────────────┐  │
         │  │ Express + socket.io  │  │
         │  │  /api  /uploads /p   │  │
         │  └──────────┬───────────┘  │
         │  ┌──────────▼───────────┐  │
         │  │  tus 上传 → SHA-256  │  │
         │  │  → CAS 落盘 → 写库   │  │
         │  └──────────┬───────────┘  │
         │  ┌──────────▼───────────┐  │
         │  │  media.db (SQLite)   │  │
         │  │  blobs/  thumbs/     │  │
         │  └──────────────────────┘  │
         └────────────────────────────┘
                      │ mDNS 广播
              （桌面端自动发现）
```

一次上传要走这几步：

1. 设备选好文件，勾选接收方（全员或某台设备），开始上传。
2. tus 把文件分片传到服务器临时区，断了能续。
3. 传完，服务器算整个文件的 SHA-256，把字节搬到 `blobs/sha256/` 对应目录。
4. 在 SQLite 里写一条版本记录，填上来源设备、时间、MIME、大小、媒体信息。
5. 异步生成缩略图。
6. socket.io 通知接收方：「你有新文件到了」。

## 七、数据模型

版本管理是这个项目的灵魂，设计上要经得起折腾。核心是**逻辑文件**和**物理字节**分开。

- **资产（assets）**：一个逻辑文件，比如「度假照片.jpg」。用户看到的是它。
- **版本（versions）**：每次上传产生一条，只增不改。记下这次的哈希、大小、来源、时间。
- **块（blobs）**：按 SHA-256 存的物理字节，不可变。同一份内容只存一次。

**打个比方**：assets 像一本书的书名，versions 像每一次再版，blobs 像印刷用的电子原稿。再版可以出很多次，原稿只要内容没变就还是那一份。

SQLite 表结构（初稿）：

```text
assets
  id TEXT PK, current_version_id INTEGER,
  created_at, updated_at

versions
  id INTEGER PK, asset_id TEXT, version_no INTEGER,
  prev_version_id INTEGER, blob_sha256 TEXT,
  original_name TEXT, mime TEXT, size INTEGER,
  source_device TEXT, uploaded_at TEXT,
  width INTEGER, height INTEGER, duration_sec REAL,
  meta_json TEXT
  UNIQUE(asset_id, version_no)

blobs
  sha256 TEXT PK, size INTEGER, ref_count INTEGER, created_at

thumbs
  blob_sha256 TEXT, kind TEXT, path TEXT,
  width INTEGER, height INTEGER, mime TEXT

devices
  id TEXT PK, name TEXT, last_seen_at TEXT

transfers
  id TEXT PK, version_id INTEGER, from_device TEXT,
  to_device TEXT（或 ALL）, created_at, status TEXT
```

目录布局：

```text
data/
  media.db
  uploads/              # tus 临时区
  blobs/sha256/ab/cdef… # 原文件，按前两位分目录
  thumbs/<hash>/320.jpg # 缩略图
```

这里有个产品决策：**哪怕内容和上一版一模一样，也记一条新版本**。历史要如实反映「你什么时候又传了一次」。CAS 只负责不重复存字节，不替用户做「去重」这个决定。

## 八、第一版做什么，不做什么

第一版（M1）的目标只有一个：**三台设备之间能稳定传原文件，服务器能看媒体库和版本历史。**

必须做：

- 服务器二维码配对，iPhone、iPad、电脑浏览器都能连入
- 选中文件，发给全员或指定设备
- 文字粘贴发送（作为特殊的文本文件）
- tus 断点续传，带进度条
- SHA-256 落盘，版本历史，按版本下载
- 媒体库：图片瀑布流、视频封面、按类型和时间筛选
- 原图预览、Range 播放视频、下载
- 启动打印局域网地址

明确不做（放进后续版本）：

- Docker 和容器化（用户说了资金充足再说）
- 端到端加密、复杂权限体系（局域网内加一道简单口令就够）
- 块级去重、增量同步（那是 Syncthing 的活，第一版用不上）
- 图片视频压缩或转码（和「不压缩」的定位冲突）
- 跨网传输、公网访问
- 网页内摄像头扫码（需要 HTTPS，成本收益不划算）

## 九、部署方式

理想情况一条命令搞定：

```bash
npm install
npm start
```

启动日志会打印出：

```text
LanDrop 已启动
局域网地址：http://192.168.1.23:3000
配对二维码已在管理页显示
```

服务监听 `0.0.0.0`，不是 `127.0.0.1`，否则手机连不上。内网 IP 用 Node 的 `os.networkInterfaces()` 拿，多网卡时让用户在页面上确认选哪个。

要长期常驻，用 pm2 托管：`pm2 start ecosystem.config.js && pm2 save && pm2 startup`。macOS 下它会自动生成 launchd 配置，开机自启。

前置条件写进 README：设备在同一个子网、路由器没开 AP 隔离、防火墙放行 3000 端口。AP 隔离会让所有局域网直连方案失效，这点必须提醒用户。

## 十、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| iPhone 切后台打断上传 | 大文件传一半失败 | 上 tus 断点续传；传输中页面用 NoSleep 思路保持唤醒 |
| HEIC 图片浏览器打不开 | 预览白屏 | sharp 转 JPEG 缩略图，原文件保留 HEIC |
| 大文件把内存撑爆 | 服务崩溃 | 全程流式落盘，绝不整文件读进 Buffer |
| mDNS 被企业网络屏蔽 | 电脑发现不了服务器 | 二维码和固定 IP 是主路径，mDNS 只是锦上添花 |
| 文件名冲突 | 版本错乱 | 版本归属按 asset_id + 来源设备，不靠文件名 |
| 版本只增不删，磁盘会涨 | 用久了占空间 | 第一版先做软删除标记；后续加淘汰策略和垃圾回收 |
| 客户端谎报 MIME | 安全风险 | 不信任 Content-Type，按文件头嗅探真实类型 |

## 十一、路线图

**M1 · 能用（本次要做）**

内网部署、二维码配对、上传与版本化、媒体库、原图预览、全员/单设备发送。目标是三台设备之间跑通。

**M2 · 好用**

设备别名管理和备注、媒体库搜索与筛选、批量操作、传输记录、版本对比、口令保护、HEIC 和视频预览增强。

**M3 · 好管**

容器化部署（Docker Compose）、可选 HTTPS 与完整 PWA、版本淘汰策略与垃圾回收、多用户与权限、外网安全访问。
